# Crypto unblocking findings

Research: 2026-10-31. Scope: engineering evidence for native PS4 synthetic-GD
authoring, not console security bypass, recovery of private inputs, or permission
to distribute embedded material. Only this findings file was changed. Existing
authoring/provenance contracts remain authoritative until maintainers integrate
these narrower results. Parallel writer work was not modified or tested.

## Outcome: gates that can actually narrow

1. **Outer-PFS algorithms do not require another fixed secret.** An explicit
   build passcode/content ID, derived image key and selected seed suffice for
   the legacy profile. Two independently authored implementations agree on
   derivation, key ordering and sector numbering. Numeric-input provenance for
   RIF/keystone/package wrapping is a different gate; it need not prevent an
   intermediate signed/encrypted PFS implementation.
2. **Small reference outer-PFS integrity is now independently checked.** A new
   Python/cryptography calculation authenticated all 91 referenced non-header
   blocks of the existing 93-block synthetic reference image, plus its header.
   This includes its indirect block and padded data. The only unreferenced block
   was clear zero block 4. This is executed evidence for that layout, not just
   successful reader traversal. Details and reproduction below.
3. **Reproducible, non-private derivation/XTS vectors are available below.** No
   proprietary numeric constants or private fixture/passcode inputs are needed.
   These can seed native tests immediately; no need to wait for licensed RIF
   material to test HMAC/XTS or key-derivation correctness.
4. **Fake-header modulus is already derivable from existing reader inputs.**
   In-memory integer comparison established `DK3_P * DK3_Q ==
   L.Keys.PkgPublicKeys[3] == L.Keys.PkgSignKey`. Thus this is not an eighth
   modulus, nor a newly missing mathematical input. Six other package wrapping
   moduli remain additional inputs. Existing approval is not automatically a
   distribution decision for a writer.
5. **Full package authoring remains blocked separately.** No new original-source
   derivation or redistribution authority was established for the debug-RIF AES/
   RSA material, two keystone HMAC constants, or six additional package moduli.
   No NP/trophy, update-binding or console compatibility gate was cleared.

## Exact legacy crypto inputs and distinctions

Use byte serialization, not locale/host-endian conversions:

```text
D[i] = SHA256(SHA256(BE32(i)) || SHA256(content_id36 || zero12) || passcode32)
image_key = D[1]
material(index) = HMAC-SHA256(image_key, LE32(index) || seed16)
XTS tweak key = material(1)[0:16]
XTS data key  = material(1)[16:32]
PFS HMAC key  = material(2)
```

L `Crypto.ComputeKeys/PfsGenCryptoKey/PfsGenEncKey/PfsGenSignKey` and F
`gen_specific_key/gen_crypto_key/keymgr_generate_keys_for_title_keyset`
independently establish these operations. No fixed vendor AES/HMAC key appears
in this chain. Passcodes are 32 **ASCII bytes**, not 16 decoded hex bytes.

New-crypt is a distinct starting-point rule: F `keymgr.c:453-465` applies
`HMAC(D[1], seed)` when deriving from a passcode with the new algorithm, but
uses a supplied ready image key directly. Never apply that transform again to
an unwrapped IMAGE_KEY. New builds using L's legacy route must not inherit
unverified new-crypt flags from an input package.

For each encrypted container record, derive `SHA256(final_record32 || D[index])`:
first 16 bytes IV, last 16 bytes AES key. `IMAGE_KEY` and `license.dat` use index
3, `license.info` index 2. Final offsets, flags and declared lengths are part of
the record; changes require re-encryption. L `PKG/Entry.cs:214-245` establishes
seven stored digests of D[i], including D[0], while wrapped slot 0 contains the
passcode instead of D[0]. Neither digest inversion nor passcode recovery follows.

The deterministic RSA encoder is fully specified in L `Crypto.cs:81-123` and
`MersenneTwister.cs:26-85`: seed MT with eight BE32 words from
`SHA256(SHA256(modulus256 || message32))`; repeatedly SHA256 12 BE32 MT outputs,
discard zero bytes, fill 221 padding bytes; form `00 02 || padding || 00 ||
message32`; compute public exponentiation with exponent 65537. This is **not**
RSA private signing. Generic PKCS#1 randomized encryption is decrypt-compatible,
but not a byte-identical oracle replacement. A generated local RSA pair suffices
to test the generic padding/exponentiation algorithm without importing package
moduli; that comparison was not executed in this research.

## Executed independent small outer-PFS verification

Input was the already generated **synthetic**, non-executable reference package
from `tests/reference/Authoring.cs`, locally at
`/tmp/opencode/fpkg-authoring-check-4/fixture/synthetic.pkg`. No private game
fixture was read. No package fingerprint, key or passcode was emitted/recorded.
The random reference-build passcode was neither needed nor recovered.

Execution: Python 3.14.8, cryptography 50.0.2, OpenSSL 3.6.5. A separate Python
calculation used existing read-side publicized fake/DK3 pairs **in memory** and
cryptography's RSA/AES/XTS primitives; it did not invoke Rust or L/F validation.

Observed assertions passed:

* Parse table, unwrap DK3 with PKCS#1 v1.5 and verify its stored digest; derive
  IMAGE_KEY entry AES material from its exact serialized table record, CBC-decrypt,
  then unwrap the image key with the existing fake pair.
* Derive signing/XTS material from seed, check header HMAC on
  `header[0:0x380] || zero(0x220)` (total `0x5a0` bytes).
* The outer image has **93 blocks and four S32 inodes**. Block 4 is the only
  all-zero stored block after the header. For this one profile, leave it clear;
  decrypt every other sector starting at sector 16 using image-relative LE64
  sector index followed by eight zero bytes. XTS library key order is
  `data_key || tweak_key`, inverse of the format's material-half order.
* Check embedded header inode's inode-block HMAC, every inode's direct references,
  the single-indirect table and all its data references against full **plaintext
  padded 64-KiB blocks**. Exactly 91 references authenticate 91 distinct blocks;
  their set equals every non-header block except 4.
* Flip first plaintext byte of each authenticated block: each recomputed HMAC
  differs from its original. This was 91 per-block mismatch checks, not a test of
  console rejection or an installed title's authenticity.

Reproduction without new builds: use the synthetic output of the documented
`tests/reference/check-authoring.py` harness and a separate Python verifier.
Container offsets are BE32 table offset at `0x18`, count at `0x10`, BE64 PFS
offset/size at `0x410/0x418`. S32 inode width `0x2c8`, blocks field `0x60`,
first signed reference `0x64`; refs are 36 bytes, 12 direct entries, then single
and double indirect. Header's embedded S64 inode starts at `0x50`, first signed
ref at `0xb8`; read inode count/block count from LE64 `0x30/0x40`. Header inode
refs have 40-byte S64 width; this executed image has only one inode block.
Walk references with checked ranges and a visited set; compare full padded
plaintext HMACs and assert coverage rather than relying on extraction success.
Use existing approved reader constants locally, never copy key bytes into notes
or public fixtures. Fresh harness outputs differ because build passcode is random;
the assertions/counts, not a package hash, are the reproducible result.

**Limits:** this authenticates a reference-produced small tree, not the parallel
native output. It does not test double/triple indirection, multi-block inode
tables, >4 GiB payloads, or a generic clear-block discovery rule. The observed
clear block is consistent with L `PFSBuilder.cs:390-394,148-160`; those lines call
it a hack, not a universal format requirement. F's `pfs_io.c:542,565` explicitly
leaves ICV checks TODO; running F alone cannot replace this integrity verifier.
PFS RSA superblock signature is separate (`F pfs.h:250-254`, `pfs.c:272-283`);
valid HMACs do not establish that RSA signature or official authenticity.

One concrete oracle trap: L serializes header `DinodeS64` refs with 40-byte
width (`PfsStructs.cs:433-463`), but its signed allocator schedules inode-block
hash writes at `0xb8 + 36*i` (`PFSBuilder.cs:367-370`). The first ref agrees;
later refs would not. The four-inode outer profile uses one inode block and
does not hit this mismatch. Do not translate that stride or cite this run as
multi-inode-block writer verification. Ordinary S32 inode-reference addressing
also must account for block-end inode padding rather than one unbroken array.

## Reproducible public synthetic known answers

Inputs below are generated test data, not title keys/passcodes. Store only the
recipes and output hashes, not derived key bytes. Let:

```python
content_id = b"ZZ0000-CUSA00000_00-SYNTHETIC0000000"  # 36 ASCII bytes
passcode = bytes(0x21 + i for i in range(32))  # disposable synthetic input
zero_seed = bytes(16)
ascending_seed = bytes(range(16))
plaintext_sector = bytes(i % 251 for i in range(4096))
padded_block = plaintext_sector + bytes(65536 - 4096)
sector_number = 19
```

Derive D[0..6], XTS and signing material exactly as above. Encrypt one 4096-byte
sector, with tweak input `LE64(19) || zero8`. Table values are **SHA256 hashes**
of the named output, including hashes of synthetic material/HMAC, never actual
key/HMAC bytes.

Executed cross-check: Python hashlib/HMAC results matched cryptography's SHA/HMAC
API; library XTS ciphertext matched a separate XTS composition using AES-ECB,
XOR and little-endian GF multiplication. For each 16-byte plaintext block:
`T = AES_tweak(LE64(sector)||zero8)`,
`C = AES_data(P XOR T) XOR T`, then update T by left shift in little-endian
128-bit arithmetic, XOR `0x87` on high-bit carry. No ciphertext stealing is
needed for this aligned sector. This is an independently composed mode check;
the primitive APIs can share OpenSSL and are not two independently audited AES
implementations. Neither L nor F was executed for these fixed-input vectors.

## Smallest safe implementation and acceptance order

1. Implement/test passcode derivation and the vectors above using existing
   maintained primitives, explicit byte order and no key/passcode Debug output.
   Add nonzero-seed vectors to catch accidental seed omission/double transform.
2. Emit intermediate S32 signed/encrypted outer PFS with explicit build-derived
   key/seed, narrow documented layout and no new fixed numeric material. Hash
   plaintext data, then indirect parents, inode block, header; encrypt last.
   Independently verify native output with the reference reader **and** a full
   reference-walking HMAC checker. Reader acceptance alone remains insufficient.
3. Exercise direct/single/double thresholds: 12/13 and 1832/1833 payload blocks
   (`floor(65536/36) = 1820` refs/table). Check indirect padding, parent hashes,
   corrupted refs, out-of-range/cyclic refs and modified unused padding. Header
   inode-table refs are S64, not ordinary S32; do not extrapolate 36-byte width.
4. Test deterministic RSA encoding with a locally generated synthetic pair and
   independently decoded padding/exponentiation before exact package vectors.
   Use slot-3 modulus derived from existing inputs where reviewed; do not import
   all upstream keys as a convenience. Six other wrapping moduli still need the
   project's explicit provenance/distribution decision.
5. Resolve debug-RIF and new-homebrew-keystone policy independently. Require
   value-specific original-source/authority documentation and a distribution
   decision, or an explicitly reviewed local-input policy. Do not silently add
   secret signing uses to `rsa`'s existing offline/public-fake-key exception
   (see `docs/dependencies-and-fixtures.md`, RUSTSEC-2023-0071). Do not substitute
   zero RIF keys, an arbitrary RSA pair, a missing license or dummy keystone and
   call it the same GD package profile.
6. Only then complete container licenses/keys/digests/PlayGo and independently
   validate whole output. NP/trophy content, full updates/remarry, real-title
   save preservation and install/launch acceptance need their own evidence.

No Cargo/build, workspace test/lint/format, graphical, reference rebuild,
console/emulator, secret-signing or private-fixture checks were run here. No
legal conclusion, complete package-writer readiness or console support is claimed.
